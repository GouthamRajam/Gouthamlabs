# M0.3: Core platform (DB, events, API, orchestrator skeleton)

**Status: done.** All five acceptance tests passed against real Postgres and Redis, with the
orchestrator and API running as real processes (2026-10-03). `13 passed` on the M0.3 tests;
the M0.2 suite is unchanged (`162 passed, 4 skipped`, where the skips are the opt-in slow
OpenLane runs that CI always runs).

## What was built (plain English)

- **Database** (Postgres, 22 tables, Alembic migration `0001`). These are all of the core tables
  from spec Part 7.6 (projects, designs, runs, tasks, artifacts, checks, events, gates,
  org units, heartbeats, …) plus the finance tables from Part 19.5 (usage records, budgets,
  credits, budget events).
- **The org chart as data.** The divisions, departments and teams from Part 6.3 now live in
  `config/management.yaml`. On start, the orchestrator loads them into the database: 70 org
  units, matching the spec's totals exactly (139 engineer instances + 7 directors/managers = 146).
- **The event stream.** Every action emits an event (21 types, Part 11.2). Each is saved to
  the database and pushed to a Redis stream, which the API serves live on `/ws/events`
  (filter by run, agent or division).
- **The orchestrator.** It turns a design run into 11 tasks (spec → architecture →
  RTL ∥ test build → verification → synthesis → DFT → floorplan → place & route →
  signoff → GDSII), assigns each to the right team's agent, and opens gates G1–G4.
  All its state is in the database, so **it can be killed at any moment and picks up where
  it left off.** Only one can run at a time (enforced by a database lock).
- **Heartbeats and the stall watchdog.** Each task reports progress tied to a measurable
  signal. If a task goes silent longer than the configured limit, the watchdog flags it
  `task.stalled` to its manager, and escalates to a human if the stall lasts. Managers
  check in on every running task on the configured cadence.
- **Usage metering.** Every model call writes a cost row immediately; usage totals are
  always computed from those rows. Tasks get a warning at 80% of budget and a **hard
  stop** at 100% (paused + escalation). Runs get alerts at 80% and 100%.
- **API.** All 16 endpoints from Part 7.7 (projects, designs, runs, tasks, artifacts,
  evidence, gates, agents, org, management dashboard, finance summary, research briefs,
  WebSocket), plus `/health` and paged `/events`.
- **A dummy agent** that runs every stage with realistic event sequences, so the whole
  machine can be exercised before real agents exist. Everything it "does" is labeled:
  summaries start with `[dummy]` and results carry `simulated: true`. Its model calls go to
  a dummy model, but they really are metered.
- **Docker Compose** now also brings up `migrate`, `api` and `orchestrator` (all healthy).

## How to run it

```bash
docker compose up -d --build --wait          # postgres, redis, migrate, api, orchestrator
curl localhost:8000/health
python backend/scripts/demo_m03.py           # full run + SIGKILL/restart demo (below)

cd backend && python -m venv .venv && .venv/bin/pip install -r requirements.txt pytest
S2S_REQUIRE_PLATFORM=1 .venv/bin/python -m pytest tests/platform -v -s
```
Each test gets its own fresh database and Redis stream. Tests use fast SLAs: a 3 s stall
limit instead of 15 min, set through a config override. The real `management.yaml` is
unchanged.

What each acceptance test proves:
1. **Design + run → tasks in the DB.** A design and a run are created via the API, then the
   tasks are read straight from Postgres: 11 tasks in flow order. RTL and test build both
   depend only on architecture (they run in parallel). The right lead agent owns each task,
   and budgets come from `budgets.yaml`.
2. **Kill mid-run → resume from last checkpoint.** The orchestrator process is SIGKILLed
   while a task is part-way through. After restart, completed tasks are not redone. The
   interrupted task restarts **at its checkpoint** (`resumed_from_step: 2`, attempt 2), and
   each of its steps committed exactly once (heartbeat steps `[1, 2, 3, 4, 5]`).
3. **`/ws/events` under 1 s end to end.** The real API and WebSocket were used, with 0.3 s
   of simulated work per step. Every persisted event arrived exactly once; the maximum
   latency was 31 ms.
4. **Silent task flagged in time.** A task goes silent; with a 3.0 s limit it was flagged
   3.08 s after its last heartbeat, sent to its manager (Juno), escalated when the stall
   lasted, and the flag cleared when the task resumed.
5. **Every model call → a costed usage row.** The dummy model's own call log (22 calls) is
   matched call-by-call to 22 `usage_records` rows. Each cost is exactly
   tokens × price from `finance.yaml`.

## Problems hit, and what was done

1. **The org structure wasn't in `management.yaml`.** The file only pointed to the spec,
   so I transcribed Part 6.3 into it. The per-division totals match Part 6.4 exactly, and a
   test pins them.
2. **`config/budgets.yaml` had a YAML syntax error** (`Euclid:{` without a space). Nothing
   had parsed it before. I fixed that one character.
3. **First version: "tool started" appeared only when its step finished.** All events were
   published at commit, so the compose demo showed p95 529 ms with 0.5 s steps, and with
   real tools it would be minutes. Live action events (status, plan, tool started/finished)
   are now published immediately. State events still wait for their commit, so the feed
   never shows work that was rolled back. Latency with the same 0.5 s steps is now max 19 ms.
   (That demo's 5 s maximum was a bug in the demo script, which paused reading the socket
   while restarting the container. Also fixed.)
4. **Metering inside the step transaction would lose cost records on a crash.** Cost rows
   are now committed immediately, on their own.
5. **Test isolation bugs.** A config override leaked between tests, and the artifact folder
   was read once at import. Both were fixed (settings are read when used).
6. **The Docker build behind this sandbox's TLS proxy** uses the same optional CA build
   secret as the EDA image. It's not needed in CI or on a normal machine.

## Known limits / notes for later

- The model gateway has only a dummy provider. Real providers and routing come with real
  agents (M0.5). The dummy price is a placeholder.
- No evidence packets yet (`/runs/{id}/evidence/{stage}` returns 404). They come with the
  Trust Layer work. `runway` in `/finance/summary` is `null` until ledger data exists (M0.9).
- `team_metrics` are not computed yet. The dashboard shows live counts, stalls and
  assignment-SLA hit rate.
- `knowledge.embedding` (pgvector) is deferred to the knowledge base milestone (M0.5).
- Only one orchestrator instance runs (by design for Phase 0). Agents run as threads
  inside it.
- The "3 identical failures → escalate" rule is implemented. The re-assign/split actions
  after a stall are for the manager runtime (M0.5).
